# Upstream's open tracker, triaged against this fork

Compiled **12 August 2026**, re-read against this repository on **25 August 2026**. Every verdict
below was decided by reading this repository, not by reading upstream's code or the threads'
conclusions. The two dates mean different things: everything said about upstream is as of the
compile date and was not fetched again, everything said about this fork is as of the re-read.

Upstream state at that date: **41 open items — 29 issues and 12 pull requests** against 91 closed
ones, read through the GitHub API. `master` at
[magwo/elevatorsaga](https://github.com/magwo/elevatorsaga) ends at `e0c55bf8`, a README edit dated
4 January 2021; the last commit that changed any code is `9a2441af`, 21 July 2015. The tag
`legacy-1.x` in this repository points at `e0c55bf8`, so anything claimed here about "what upstream
does" can be checked with `git show legacy-1.x:<file>`. Beware 21 November 2022, which the API
reports and which is the repository's last _push_ — the branch behind PR #137 — and not a commit on
`master`.

Three verdicts are used, and they mean different things:

- **Closed here** — the complaint cannot be reproduced against this repository, and there is a named
  piece of code that is the reason why. A plausible-looking fix was not enough to earn this verdict;
  where the evidence is a measurement rather than a reading, the measurement is described.
- **Open here** — the defect or the gap is present now. Each entry says what would have to change
  and where.
- **Not applicable** — the code the report names is gone, the report is not a request, the behavior
  is deliberate, or the patch is against a document this fork no longer has.

References to this repository's code are by symbol and file rather than by line, for the reason
`docs/fork-survey.md` gives: line numbers rot on the next commit and a symbol name is always
greppable. References to `legacy-1.x` do carry line numbers, because a tag does not move.

## What is worth doing

Ranked by what it buys this repository, not by how loud the thread was. Items struck from here are
not withdrawn but shipped; the tables above are the record of what closed them, and of what each
one left behind.

1. **Decide about #4 in public** — the complaint is real and now measured, and the fork has never
   answered it. _Cost:_ very high if the answer is new levels, since each needs sizing against
   reference programs the way `2e90995` did; near zero if the answer is to leave the ladder alone
   and say so in README. _Risk:_ the expensive option is also the dangerous one — retuning levels
   1–18 breaks this fork's own promise that a legacy solution is scored by the same rules, which
   README states and `src/game/chapter1.test.ts` enforces. A nineteenth level was the safe shape of
   this answer, and the thirteen levels of chapter two are that shape at scale — a whole block beside
   the ladder, with 1–18 untouched. They are not an answer to #4, and it is worth being exact about
   why: the complaint is about the rungs a beginner actually climbs, and a beginner still meets
   level 1 first, where the naive program still passes on every seed. What the block does settle is
   the cost line above. Building beside the ladder is now the demonstrated option and not the
   theoretical one, so the choice left is a genuine one between two shapes of answer rather than
   between an answer and a risk.

2. **Horizontal room in the waiting area** — the unshipped half of PR #73. _Cost:_ moving
   `FIRST_ELEVATOR_X` and the spawn band, which invalidates every screenshot and any end-to-end
   assumption about coordinates. _Risk:_ moderate cost for a cosmetic gain, and the pressure it
   relieves is partly relieved already by `fitElevatorCount`. Worth doing only alongside other
   layout work.

3. **PR #132's one word** — _Cost:_ four strings. _Risk:_ none, but it should be adopted only if
   the maintainer agrees with the reading, which is arguable; "programs" is not obviously a typo.

Left off deliberately: **#46** (the duplication is real, but generation is a large refactor and the
drift it would prevent is already prevented by tests), **#66** and **#107** (both would widen the
player API's contract for a small audience, and #107 already works in practice), **#114** (a design
project rather than a fix), and **PR #93's** second condition (a move limit plus a wall-clock limit
is a fourth way to say what three existing conditions already say).
